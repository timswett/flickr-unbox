# Contributing / Project Conventions

Working notes for how this repo is built and maintained. Written down here
rather than left in chat history so the reasoning survives.

## Folder structure

- Personal/private data and this repo are kept physically separate. Nothing
  in this folder should ever reference a real, personal file path
  (e.g. `/Volumes/EAGET/...`) — scripts take paths as CLI args or read them
  from a config file/env var instead.
- `test_data/` holds only synthetic fixtures generated by
  `tools/generate_test_fixtures.py`. No real photos or personal metadata,
  ever.
- `tools/` holds dev utilities, not part of the shipped pipeline:
  `generate_test_fixtures.py` (fully synthetic, its output is committed —
  see `test_data/` above) and `build_private_test_fixture.py` (operates
  on a real Flickr export; a contributor validating changes against
  real-world data, or anyone wanting to try the pipeline on a small
  subset before pointing it at their whole library. Its output is
  gitignored and must never be committed).
- One README as the entry point — what this is, why it exists, how to run
  it, current status.

## Commenting

- Every script starts with a header block: purpose, usage, and — most
  importantly — what edge case(s) it exists to handle. Several of the
  fixes in this pipeline (the GPS decimal regex, the last-vs-second-to-last
  ID fallback, the disk-space check before a batch write) aren't obvious
  from the code alone; the comment explaining *why* lives right next to the
  code, not just in a README or design doc.
- Inline comments explain *why*, not *what*. Code should be readable enough
  that restating it in English would be redundant.
- No commented-out dead code. A dry-run mode is a flag/variable, not a
  duplicate line with `#` in front of it.

## Testing

- Any destructive step defaults to a dry run, with `--no-dry-run` required
  to act for real (the shipped Python CLI's model — supersedes the
  original bash pipeline's paired `foo.sh`/`foo_dryrun.sh` scripts, which
  risked the two drifting out of sync). Dry-run isn't a lightweight
  preview: it runs the stage's *full* pre-flight validation and prints the
  full summary, and only skips the final destructive action. `--no-dry-run`
  re-runs that same validation from current on-disk state rather than
  trusting an earlier dry-run, since data can change between the two
  invocations.
- Synthetic fixtures only, checked into the repo, with a hand-verified
  "golden master" expected-output file (`expected_rename_plan.tsv`-style)
  so a reimplementation can be diffed against known-correct output instead
  of eyeballed.
- New pipeline code is validated against the fixture as it's written, not
  after the fact.
- `bandit -r src/ -c pyproject.toml` (Python-specific static security
  scan) is run periodically and expected to stay clean; findings are
  either fixed or suppressed inline with `# nosec <code>` plus a one-line
  reason, never silently ignored.
- Real-data validation (`tools/build_private_test_fixture.py` against a
  real Flickr export) is a second, ad hoc tier on top of the synthetic
  suite — not committed to the repo (needs personal data, can't run in
  CI), but run against real data before trusting any pipeline change at
  scale.

## Script behavior

- No hardcoded personal paths — CLI args or a config file.
- Prefer idempotent scripts: safe to re-run without duplicating work or
  corrupting state.
- Batch operations log-and-continue rather than abort-on-first-failure
  (matches the call made on the flatten script after the `._*` junk-file
  issue) — a single bad file shouldn't kill an hours-long run.
- Defensive checks (disk space, file existence) before anything
  destructive, matching the pattern in `exif_write_batch.sh`.

## Commits

- Small, atomic commits — one logical change each. (The initial scaffold
  commit was a one-time exception to stand up the skeleton.)
- Plain descriptive messages — what changed and why. No enforced prefix
  format (not using Conventional Commits).

## Branching

- Straight commits to `main` while this is a solo project. Revisit if/when
  there are other contributors.

## CI

- No GitHub Actions workflow configured. The test suite is synthetic/
  hermetic (no privacy concern running it anywhere) and would run
  cleanly in CI as-is if one is added.
